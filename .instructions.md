# Project Instructions

This repository is a full-stack TypeScript application:

* **Backend** — Express 4 + Knex, run directly from TypeScript with `tsx`
  (`server.ts`). Routers live in `src/api/*`.
* **Frontend** — React 19 + React Router 7 SPA built by Vite, in `src/`.
* **Database** — Azure SQL / MS SQL Server in production, SQLite locally.
  Both are configured from a single `knexfile.ts`.

Both are served by the same Node process and deployed together to Azure App
Service.

## The most important rule: the database is the single source of truth

Earlier versions of this app were a localStorage prototype, and several
features were left half-migrated: a handler would write to `localStorage` and
never call the API that already existed. That caused real, user-visible
failures — admin notifications that vanished seconds after being sent,
training materials no CSR could ever see, a profile-photo button that did
nothing at all.

So:

* **Any state another person must see goes through the API.** If two users
  should see the same thing, `localStorage` is the wrong place for it.
* `localStorage` is only for per-device conveniences: the theme, and the
  auth token.
* `src/utils/localStorage.ts` still exists for those cases. Do not use it to
  persist business data.
* `src/utils/logger.ts` no longer records anything. The audit trail is the
  `audit_logs` table, written by `logAction()` in `src/api/audit.ts`. Log
  every state-changing operation there, server-side.

## Deployment constraints — read before adding a dependency

**Do not add a new runtime npm dependency.** `wwwroot/node_modules` on the
App Service is frozen and the deploy does not refresh it, so a newly added
package is missing at runtime and the site returns 503. See
`docs/DEPLOYMENT.md` for the full story and what would unblock it. This also
means you cannot `import` a package that is listed in `package.json` but not
already imported somewhere in shipping code — `zod` is the notable example.

**Migrations do not run on deploy** (`SKIP_DB_MIGRATIONS=true`). They are
applied by hand via `POST /api/admin/run-migrations` as a superadmin. Write
every migration defensively with `columnExists()` / `tableExists()`, and make
the code that uses a new column degrade cleanly when it is absent — the app
ships before the schema does. `/api/health` reports the pending count.

## Engineering style

* Keep changes focused; match the surrounding code's style.
* Tailwind classes, consistent with the existing components.
* Preserve Mongolian label text exactly as specified.
* Validate on the SERVER. Client-side checks are a convenience, not a rule —
  anything that matters must be enforced in `src/api/*`.
* Prefer existing helpers (`src/utils/sqlDate.ts` for dates,
  `src/utils/excel.ts` for exports) over new ad-hoc ones.

## Dates and times

Mongolia is UTC+8 and does not observe DST; Azure App Service runs in UTC.
Never read calendar fields off a `Date` with `getFullYear()`/`getHours()` on
the server — that yields the UTC wall clock, not the user's. Use
`src/utils/sqlDate.ts`.

## Clarifications

If a request is ambiguous, ask:
- Whether the rule applies globally or to specific dashboards.
- Which user roles are affected.
- Whether it is a hard requirement or a preference.
